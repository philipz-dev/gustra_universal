Apple look (HIG) — simple words

What is HIG?

HIG = Apple’s rulebook for how iPhone apps should feel. Buttons, menus, swipe, alerts — so the app feels “at home” on an iPhone.

Why it matters

Apple’s editors like apps that feel native. That helps for App Store stories (like App of the Day). It is not a promise — you also need a good story and a nice product page.

Gustra’s big “oops” moments (what to change)

  1. Alerts — we use our own popups instead of the normal iPhone ones.
  2. Menus — Options / Share / Take photo use custom sheets instead of the system menu from the bottom.
  3. Swipe to delete — our own swipe, not the normal list swipe.
  4. Green top bar everywhere — fine for brand, but less “standard iPhone”. Keep the look; fix the menus first.
  5. Bigger text / VoiceOver — make the app easier for everyone (Apple cares a lot).

Do first (safe)

System menus for Take/Import, Options, and Share.

Do later

Swipe, accessibility (bigger text / VoiceOver).

Keep

Forest green House look (nav, stars, cream). Brand is good — only the system menus/alerts/swipe should feel more like iPhone.

Upload for testers (TestFlight / Play Internal)

Only for testers — not an App Store or Play Store public release. Completing Play “Send for review” for policy/listing is not a public Production release.

  • iOS → TestFlight (upload; Internal/Developer via ASC automatic distribution)
  • Android → Play Internal testing · package net.gustra.app

How to run

npm run deploy  (or deploy:ios / deploy:android)

What the script asks

  1. Platform: 1 iOS / 2 Android / 3 both
  2. iOS TestFlight group: D Developer (default) / I Internal — reminder only; upload has no eas.json groups (Apple rejects API assign when automatic distribution is on)
  3. Shows a summary of what upload would do
  4. Upload? type Y twice (double confirm) — anything else stops

Build mode (script change)

  • Default = local — eas build --local on this Mac (no EAS cloud queue / fewer credits)
  • Local iOS needs fastlane on PATH: brew install fastlane (missing → eas-cli-local-build-plugin … exited with non-zero code: 1)
  • Local builds cannot use --auto-submit. The script: build --output → eas submit --path (not --latest)
  • Cloud — npm run deploy:cloud or npm run deploy -- --cloud (still uses auto-submit on Expo servers)
  • Old cloud-only script frozen at scripts/deploy-store.eas-cloud-backup.sh

Useful flags

  • npm run deploy -- --go — skip overview, jump to double Yes
  • npm run deploy -- --platform android --go
  • npm run deploy -- --go --platform ios. Env: DEPLOY_PLATFORM, DEPLOY_BUILD_MODE, DEPLOY_IOS_GROUP / --ios-group Developer|Internal (default Developer)
  • Non-interactive confirm: DEPLOY_CONFIRM1=Y DEPLOY_CONFIRM2=Y
  • If empty CI= breaks EAS: run with CI=false

Credentials

  • npm run deploy:credentials — checklist for Play service account JSON + optional ASC API key
  • Play SA path in eas.json: secrets/gustra-503718-….json; invite gustra-backend@….iam.gserviceaccount.com as Release manager on net.gustra.app

After both Yes: bump shared build (ios.buildNumber = android.versionCode → same N) → build → submit → one git commit. Solo iOS/Android still bumps both so they stay aligned. On failure the bump stays.

This never submits a public App Store / Play production track release.

Clean Metro / Expo start

When the bundler is stuck, port 8081 is busy, or you still see an old error after a fix:

  • npm run gustrarun — kill stuck Expo/Metro + free :8081 + start Metro (--localhost), prewarm JS bundle, then open booted simulators. Applies DevTools autolinking hang patch
  • npm run gustrarun -- --clear — same, but also clear Metro cache
  • npm run gustrarun -- --skip-prewarm — open apps immediately (may show “Could not connect” on cold first bundle)
  • npx kill-port 8081 && npx expo start -c — free Metro port + start with cleared cache (Metro only)

Local EAS build → submit

  • brew install fastlane required for local iOS archive
  • After local build, submit the local file (--path build-N-ios.ipa) — never --latest (that re-uploads the newest cloud build, e.g. an old build 28 while you just built 31)
  • deploy-store.sh writes build-<n>-ios.ipa / build-<n>-android.aab via eas build --local --output then eas submit --path

Sentry (crash reporting)

  1. Create a React Native project at sentry.io
  2. Local .env / .env.local: EXPO_PUBLIC_SENTRY_DSN, SENTRY_ORG, SENTRY_PROJECT, SENTRY_AUTH_TOKEN
  3. Local iOS archive: deploy-store.sh injects those into eas.json production.env for the build only (shell alone is not enough). SENTRY_ALLOW_FAILURE=true so a bad/missing token never fails TestFlight
  4. Cloud EAS: same names as sensitive env on expo.dev
  5. New native build required after adding the plugin (npm run deploy)
  6. __DEV__ Settings → Advanced → “Send Sentry test event”
